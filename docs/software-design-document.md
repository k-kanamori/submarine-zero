## 2. 設計目的

企画書で定義した次の体験を、PCブラウザ上で安定して実現する。

- 三人称視点による6自由度の潜水艦操作
- 暗い氷海における視覚とソナーを使った索敵
- 誘導魚雷と手動魚雷による爽快な戦闘
- 通常敵10隻前後と円盤型巨大潜水艦のボス戦
- チェックポイント、リザルト、機体アンロック
- 主人公と20年来の付き合いがあるAI相棒による物語進行

本書は実装責務、データ構造、処理順序、品質基準を定める。演出の秒数、武器威力、敵速度などの調整値は初期値として扱い、プレイテストを通じて変更できる構造にする。

## 4. 採用技術

| 分類 | 採用候補 | 用途 |
| --- | --- | --- |
| アプリ | Next.js App Router | 画面の入口、静的配信、アセット分割 |
| 言語 | TypeScript | ゲームデータと状態の型安全性 |
| UI | React | メニュー、HUD、字幕、設定画面 |
| 3D | Three.js | WebGL描画、シーン、カメラ、マテリアル |
| React統合 | React Three Fiber | Reactコンポーネントとして3Dシーンを構築 |
| 物理 | Rapier／React Three Rapier | 衝突、センサー、剛体、固定時間ステップ |
| 状態管理 | Zustand | 低頻度のゲーム状態、HUD、設定、セーブ状態 |
| 音響 | Web Audio API | 3D音響、ミキシング、ローパス、音量制御 |
| 単体テスト | Vitest | 数式、状態遷移、データ検証 |
| E2E | Playwright | 画面遷移、入力、セーブ、再開 |

Next.jsはApp Routerを使う。ゲーム本体はブラウザAPIとWebGLに依存するためクライアントコンポーネントとし、WebGLキャンバスを動的ロードする。UIの静的な外枠はNext.js側で先に表示し、ゲーム用JavaScriptと3Dアセットの読込中は専用ローディング画面を出す。

React Three FiberはThree.jsのReactレンダラーとして採用する。物理はReact Three Fiberの描画ループと連動でき、固定時間ステップを扱えるReact Three Rapierを採用候補とする。React 19系を使う場合はReact Three Fiber 9系、React Three Rapier 2系の互換系列をそろえる。

### 依存方向

- Contentは純粋なデータとしてSimulationから参照する。
- SimulationはReactコンポーネントやDOMを参照しない。
- PresentationはSimulationの読取用スナップショットとイベントを購読する。
- Screen UIはZustandストアを通じて低頻度状態を参照する。
- InfrastructureはブラウザAPIを包み、Simulationへ抽象インターフェースを提供する。

### 状態の分離

| 状態 | 保管場所 | 更新頻度 | 例 |
| --- | --- | --- | --- |
| シミュレーション状態 | GameWorld内のオブジェクト | 毎固定ステップ | 位置、速度、魚雷、敵AI |
| セッション状態 | Zustand session slice | イベント時 | ゲーム進行、HP、目標、ポーズ |
| UI状態 | Zustand ui slice | 操作時 | メニュー、字幕、照準対象 |
| 設定 | Zustand settings slice | 設定変更時 | 音量、感度、反転 |
| 永続状態 | SaveData／localStorage | チェックポイント等 | アンロック、クリア、設定 |

位置や速度を毎フレームReact stateへ書き込まない。描画対象は参照を介して更新し、HUDに必要な値のみ低い頻度でストアへ反映する。これにより不要なReact再描画を防ぐ。

## 8. ゲームループ

### 時間管理

- 物理とゲームロジックは60Hzの固定時間ステップで更新する。
- 描画はブラウザのrequestAnimationFrameに合わせる。
- 描画間隔が変動してもゲーム挙動が変わらないよう、経過時間をaccumulatorに蓄積して固定ステップを複数回処理する。
- 1描画で処理する固定ステップは最大5回とし、長時間停止後の追いつき処理によるフリーズを防ぐ。
- カメラと見た目は直前と現在のシミュレーション状態を補間する。

### 1ステップの処理順

1. 入力スナップショット取得
2. ミッション状態更新
3. プレイヤー操縦入力の変換
4. 敵AIの意思決定
5. 推進力、回転力、浮力の適用
6. 武器、再装填、魚雷誘導の更新
7. 物理ワールド更新
8. 衝突とセンサーイベント収集
9. ダメージ、撃破、報酬の確定
10. ソナー接触情報の更新
11. ゲームイベント発行
12. HUD用スナップショット更新

同一ステップ内で結果が実行順に左右されないよう、衝突やダメージは一度キューへ積み、物理更新後にまとめて解決する。

## 9. 座標系と単位

- 右手座標系を採用する。
- X軸は右、Y軸は上、Z軸は後方とし、機体前方はローカル-Zとする。
- 1ワールド単位を1メートルとして扱う。
- 深度は海面Y=0から下向きの距離として depth = max(0, -position.y) で求める。
- 角度は内部でラジアン、UI表示時のみ度へ変換する。
- 速度は内部でm/s、HUDでは必要に応じてノット相当表記へ変換する。

第1ステージは原点から数km以内に収め、極端に広い座標による浮動小数点精度低下を避ける。

## 10. 入力設計

### 論理アクション

物理キーではなく論理アクションをSimulationへ渡す。

| アクション | キーボード初期値 | ゲームパッド初期値 |
| --- | --- | --- |
| thrust | W／S | 左スティックY |
| strafe | A／D | 左スティックX |
| ascend | Space | 右バンパー |
| descend | Ctrl | 左バンパー |
| yaw | マウスX／左右キー | 右スティックX |
| pitch | マウスY／上下キー | 右スティックY |
| boost | Shift | 左スティック押込 |
| activeSonar | Q | フェイスボタン上 |
| lockTarget（ロック・対象切替） | E／右クリック | 左トリガー |
| fireWeapon | 左クリック | 右トリガー |
| cycleWeapon | マウスホイール | フェイスボタン左 |
| deployMine | R | フェイスボタン右 |
| deployDecoy | F | フェイスボタン下 |
| pause | Escape | Menu |

左右バンパーを上昇・下降、左右トリガーをロック・射撃として役割を分ける。現在の実装では、Eキー、右クリック、左トリガーは同じ対象選択処理を呼び出し、押すたびにロック対象を切り替える。押し続けている間の自動巡回は行わない。右クリックのブラウザ標準メニューはゲームのCanvas上で抑止する。最終的なボタン名表示は接続中のゲームパッド形式に合わせる。

### 入力処理

- スティックのデッドゾーン初期値は0.15。
- デッドゾーン後の値は曲線補正し、微操作と最大入力を両立する。
- マウス感度、Y軸反転、スティック感度、振動を設定可能にする。
- Gamepad APIは接続順に監視し、最後に入力されたデバイスに応じて画面上の操作表記を切り替える。
- ポーズ中の入力はUIへだけ渡し、機体操作へ伝播させない。

## 11. 潜水艦移動

### 設計方針

完全な流体シミュレーションは行わない。剛体に推進力、回転トルク、線形抵抗、角抵抗を与え、重厚さと操作性を調整値で作る。

### 更新モデル

    force =
      forwardAxis * thrustInput * forwardForce
      + rightAxis * strafeInput * strafeForce
      + upAxis * verticalInput * verticalForce

    dragForce = -velocity * linearDrag
    torque = desiredAngularVelocityとの差を埋めるPD制御

### 初期調整値

| 項目 | 初期値 | 備考 |
| --- | ---: | --- |
| 最大前進速度 | 18 m/s | ブースト時は24 m/s |
| 最大後退速度 | 7 m/s | 前進より遅い |
| 最大横移動速度 | 6 m/s | 回避用 |
| 最大上昇下降速度 | 8 m/s | 狭所で扱える速度 |
| 最大ヨー速度 | 35度/秒 | 重さを感じる範囲 |
| 最大ピッチ速度 | 28度/秒 | 画面酔いを抑える |
| 加速時間 | 約1.8秒 | 0から巡航速度まで |
| 制動時間 | 約1.2秒 | 操作の快適性を優先 |

姿勢のロールは見た目として旋回方向へ最大8度傾けるが、照準と上下感覚を壊さないよう自動で水平へ戻す。

## 12. カメラ

### 通常カメラ

- 機体後方12〜18m、上方4〜7mの範囲で機体サイズに合わせる。
- 位置追従にはばねモデルを用い、回転追従は位置よりわずかに速くする。
- 地形との間にレイキャストを行い、遮られる場合は機体へ寄せる。
- 速度上昇時はFOVを最大8度広げ、急旋回時は機体の横方向が見えるようオフセットする。

### ロックオンカメラ

- 自機、進行方向、標的の3点を考慮して注視点を補間する。
- 標的が背後へ回った場合は無理にカメラを反転せず、画面端インジケーターへ切り替える。
- 魚雷命中演出は原則として通常カメラを奪わない。最後の敵やボス撃破時だけ短い演出カメラを許可する。

## 13. ソナー設計

### 接触情報

各探知対象にContactを持つ。

| フィールド | 内容 |
| --- | --- |
| entityId | 対象ID |
| confidence | 探知確度。0〜1 |
| estimatedPosition | 推定位置 |
| estimatedVelocity | 推定速度 |
| classification | unknown／vehicle／torpedo／creature |
| disposition | unknown／hostile／neutral |
| lastDetectedAt | 最終探知時刻 |

### パッシブソナー

- 対象の騒音値、距離、自機の受信性能、地形遮蔽から探知確度を更新する。
- 敵の高速移動、魚雷発射、衝突は一時的に騒音値を上げる。
- 探知確度が低い場合は曖昧な方位のみ、高い場合は位置、分類、速度を順に開示する。
- 未更新のContactは時間とともに確度が低下し、推定位置だけが進行方向へ移動する。

### アクティブソナー

状態はready、charging、emitted、cooldownの4段階とする。

1. 入力で短いチャージを開始。
2. パルスを球状に拡大する。
3. パルスが対象へ到達した時点で地形遮蔽を判定する。
4. 有効対象のContact確度を大きく上げる。
5. プレイヤー位置を示すNoiseEventを敵AIへ通知する。
6. クールダウン終了後に再使用可能にする。

初期値は有効半径600m、チャージ0.4秒、往復を感じさせる表示時間1〜2秒、クールダウン6秒とする。数値はステージサイズと戦闘密度に合わせて調整する。

### 探知式の基準

厳密な音響計算ではなく、調整可能なスコアで判定する。

    detectScore =
      targetNoise
      + receiverSensitivity
      + activePingBonus
      - distanceLoss
      - occlusionPenalty
      - ambientNoise

スコアを0〜1へ正規化してconfidenceの目標値とし、急激な表示切替を避けるため時間補間する。

### ロックオン対象選択（実装済み）

`targetLock.ts`の`nextLockTarget(enemies, currentId, position, now)`は、次の対象IDまたは`null`を返す。敵配列や敵の状態を書き換えない。

1. `alive && spawned`で、`detectedUntil > now`または自機との3次元距離が115ワールド単位未満の敵を候補にする。
2. 候補が0隻なら`null`を返す。
3. 現在の対象IDが候補内にあれば、敵配列の順序で次の候補を選ぶ。末尾から先頭へ巡回し、候補が1隻なら同じIDを返す。
4. 初回、または現在の対象が候補から外れた場合は、候補のうち自機に最も近い敵を選ぶ。同距離なら敵配列で先にある候補を優先する。

巡回中は距離順に再ソートしない。敵の移動によって選択が一部の候補間を往復し、他の候補を選べなくなることを防ぐ。ボスも同じ候補条件を満たせば選択できる。

現在の対象は`UnderwaterGame.tsx`の`lockId`に保持する。探知期限切れだけでは既存ロックを自動解除せず、次の選択操作ではその時点の候補条件で選び直す。対象が撃破済み・未出現・存在しない状態ならHUD更新時に解除する。候補がない状態での選択操作は、解除とともにAIの案内を表示する。ロック対象の変更は以後に発射する誘導魚雷の対象に反映され、発射済み魚雷の対象IDは切り替えない。

本節は現行プロトタイプの選択条件であり、前述の`Contact.confidence`を用いる高度な探知モデルは今後の設計とする。

## 14. 武器設計

### 共通状態

ready、firing、reloading、disabledを共通状態とする。発射要求時に再装填、射程、ロック条件を検証し、成功した場合だけProjectileSpawnEventを発行する。

### 誘導魚雷

- 現行実装ではロック対象IDを誘導先として使用する。`Contact.confidence`によるロック確度の閾値判定は今後の拡張とする。
- 発射後は一定時間直進し、安全距離を取ってから誘導を開始する。
- 比例航法を簡略化した旋回制御で予測迎撃点へ向かう。
- 視野角外、最大追尾時間超過、デコイへの乗り換えでロックを失う。
- 魚雷の旋回性能は潜水艦より高いが、急反転には追従できない。

### 手動魚雷

- 照準方向へ直進し、ロックを必要としない。
- 誘導魚雷より高威力または短い再装填時間を与える。
- 敵の進路を読んだ命中に追加報酬や演出を付ける案を残す。

### 機雷

- 自機後方へ低速放出する。
- 起動遅延後、敵対対象がセンサー半径へ入ると爆発する。
- プレイヤー自身には爆発ダメージを与えないが、爆風演出と警告は出す。
- 一定時間または同時設置上限を超えると古い機雷から消滅する。

### デコイ

- 数秒間、通常機体より高い音響シグネチャを発する。
- 敵魚雷は現在対象とデコイの誘引スコアを比較し、条件を満たすと目標を変更する。
- 必ず成功する防御ではなく、投入タイミングと距離で成功率を変える。

### 爆発とダメージ

爆発中心からの距離でダメージを減衰させる。直撃には追加倍率をかける。1固定ステップ内に同じ爆発が同じ対象へ複数回適用されないようeventIdで重複排除する。

## 15. HPと撃破

EntityHealthはcurrent、maximum、invulnerabilityUntilを持つ。被弾時はDamageEventを通じてHPを減らし、0以下でDestroyedEventを一度だけ発行する。

- プレイヤーは被弾直後に短い無敵時間を設け、重なった当たり判定による即死を防ぐ。
- 通常敵は撃破後に当たり判定とAIを停止し、残骸演出へ移行する。
- 爆発VFX、残骸、報酬確定は撃破イベントの別購読者として分離する。
- ボス撃破時はミッション進行が完了するまで入力を維持し、その後リザルトへ遷移する。

現行実装では、ボス撃破時に`completed.current = true`として3.2秒のクリア演出を開始する。敵魚雷の対自機命中処理は`!completed.current`を条件に含め、演出中はHP減算、被弾警告、魚雷による撃沈・リスポーンを発生させない。撃破前に発射された敵魚雷にも同じ条件を適用する。

## 16. 敵AI

### 共通状態

    patrol
      → suspicious
      → investigate
      → engage
          → evade
          → reposition
          → engage
      → search
      → patrol
      → destroyed

### 認識

- 敵も視界ではなくContactモデルを使ってプレイヤーを認識する。
- プレイヤーのアクティブソナー、魚雷発射、ブースト、衝突をNoiseEventとして受け取る。
- 敵ごとに記憶時間を持ち、見失った後は最後の推定位置を捜索する。

### 通常敵

| 種類 | 役割 | 行動 |
| --- | --- | --- |
| 哨戒無人艇 | 発見役 | 高感度ソナーで接触し、仲間へ共有 |
| 攻撃潜水艇 | 主戦力 | 中距離を維持し誘導魚雷を発射 |
| 機雷敷設艇 | 進路妨害 | プレイヤーの移動先へ機雷を配置 |

全10隻を同時に戦わせない。区画ごとに2〜4隻を配置し、未交戦の敵は低頻度AIへ落としてCPU負荷を抑える。

外観は通常敵3種（`scout`、`hunter`、`layer`）でたいげい型モデルを共有する。`hunter`のみ表示スケール1.15、他は1とする。今回の外観変更では敵AI、当たり判定、魚雷発射位置を変更しない。アセットの構成は第24節を参照。

### 操舵

目的地点へのseek、障害物を避けるavoid、仲間から離れるseparationを重み付けして目標速度を作る。複雑な海中ナビゲーションメッシュは初期版では使わず、区画ごとのウェイポイントグラフと前方レイキャストを組み合わせる。

## 17. ボス設計

### 状態とフェーズ

| フェーズ | HP | 主な行動 |
| --- | --- | --- |
| 潜伏 | 戦闘開始前 | 偽反応と護衛艇で追跡を妨害 |
| Phase 1 | 100〜70% | 円盤外周を回転、複数方向へ魚雷発射 |
| Phase 2 | 70〜35% | ソナー衝撃波、発射口の攻撃頻度上昇 |
| Phase 3 | 35〜0% | 氷床破壊、落下氷塊、中央弱点露出 |
| Destroyed | 0% | 制御喪失、爆発、識別情報の発見 |

### 部位

- 外周発射口：複数。破壊すると同時発射数が減る。
- ソナー発生器：衝撃波の予兆を発し、破壊でクールダウンが延びる。
- 中央コア：通常時は装甲で保護し、条件成立時だけダメージが通る。

ボス本体のHPと部位HPを分離する。部位破壊は攻略を有利にするが、全破壊を必須にはしない。弱点露出条件は時間経過ではなく、部位破壊または特定攻撃後の隙で作る。

## 18. 巨大タコ拡張設計

巨大タコは独立したEncounterとして追加できるようにする。

- 触腕は個別Entityとして本体に紐付ける。
- 墨は視覚効果だけでなく、ソナーconfidenceを減衰させるVolumeとして扱う。
- 拘束はPlayerControlModifierを適用し、移動性能を一時的に低下させる。
- 撃破報酬の機体はDiscoveryTriggerからUnlockEventを発行する。

初期リリースから外す場合も、ステージデータ内に遭遇入口と報酬地点を追加できる構造を維持する。

## 19. ミッションとステージ

### MissionObjective

目的はactive、completed、failed、hiddenを持つ。第1ステージでは次の目的を順に有効化する。

1. 海域へ侵入する。
2. 不明なソナー反応を追跡する。
3. 護衛艇を突破または回避する。
4. 観測施設へ到達する。
5. 円盤型巨大潜水艦を発見する。
6. 標的を撃破する。
7. 識別情報を回収する。

通常敵10隻は配置数の目安であり、全撃破を必須にしない。戦闘中心の体験を保ちつつ、見つからずに一部を回避する選択も認める。

### ステージ区画

| 区画 | 役割 |
| --- | --- |
| Entry | 操作導入、浅層の光 |
| Ice Field | ソナー導入、氷塊による遮蔽 |
| Wreck | 武器とデコイ、発見機体 |
| Trench | 深度による暗さ、隠しルート |
| Boss Arena | 円盤型潜水艦、落下氷塊 |

区画境界には非表示Triggerを置き、敵、会話、チェックポイント、BGMを有効化する。遠方区画は描画距離、LOD、低頻度更新を用いて負荷を抑える。

## 20. チェックポイント

### 保存対象

- チェックポイントID
- プレイヤー機体IDとHP
- 武器の再装填状態
- 完了済みObjective
- 撃破済みの重要Entity
- 発見済みDiscovery
- 一度再生した会話ID
- ステージ用乱数seed

### 復元手順

1. 現在のシミュレーションと音を停止する。
2. 対象ステージの初期データを再構築する。
3. チェックポイントスナップショットを適用する。
4. 撃破済みEntityと消費済みTriggerを除外する。
5. プレイヤーを安全な復帰地点へ配置する。
6. カメラ、ソナーContact、一時VFXを初期化する。
7. 短い無敵時間を付けてplayingへ戻す。

Rapierの物理ワールド全体をそのまま永続化せず、ゲーム上必要な論理状態から再構築する。これによりコンテンツ変更後の互換性とデバッグ性を保つ。

## 24. レンダリング

### シーン

- 3DモデルはglTF 2.0形式を基本とする。
- 静的な氷塊や構造物は可能な範囲でインスタンシングする。
- 潜水艦、魚雷、重要オブジェクトは距離別LODを用意する。
- 遠方の小物と泡はGPUパーティクルまたはInstancedMeshで描画する。
- 透明物の重なりを抑え、半透明の水表現を画面全体のポストプロセスへ寄せる。

### たいげい型の通常敵モデル（実装済み）

参考画像をもとにBlenderで制作した外観モデルを使う。形状の特徴は丸い艦首、黒い船体、前寄りの艦橋と潜舵、X字尾舵、側面アレイ、7枚羽根のスクリュー。実艦の精密な寸法・内部構造・性能の再現は目的としない。

| 項目 | 現行アセット |
| --- | --- |
| 編集元 | `assets/taigei/taigei.blend`、編集用47パーツ |
| 再生成 | Blenderで`build_taigei.py`、続けて`export_taigei.py`を実行 |
| 配信URL | `/models/taigei.glb` |
| GLB構成 | 船体`Taigei_Hull`、スクリュー`Taigei_Propeller`の2ノード |
| 描画量 | 10,448三角形、5描画、253,764バイト |
| 外部依存 | 外部テクスチャなし。カメラ・ライトはGLBに含めない |
| 座標系 | Blender：艦首+Y・上+Z、glTF／ゲーム：艦首-Z・上+Y |
| ゲーム内寸法 | 全長約9.57ワールド単位、`hunter`は1.15倍 |
| 回転中心 | スケール適用前のゲーム座標でZ=4.82 |

生成スクリプトは既存シーンを残して専用シーンを作成し、出力スクリプトはゲーム用に部品を統合する。編集用ファイルにはプレビュー用スタジオも保存する。参考画像、再生成方法、プレビューは[アセット仕様](../assets/taigei/README.md)を参照。

`TaigeiModel`は`useLoader(GLTFLoader, ...)`で読込を共有し、glTFのメッシュ変換を保持して描画する。スクリューは艦ごとのグループでゲーム座標のZ軸を中心に回転させる。元モデルのジオメトリを共有し、ソナー対応マテリアルにはBlenderの色・金属度・粗さを引き継ぐ。敵用ソナー反響は従来の橙色を維持し、レーダー上の緑色ロック表示とは別に扱う。

`EnemySubmarine`は通常敵のみ`TaigeiModel`へ切り替え、円盤型ボスのモデルは維持する。

### 水中表現

- 深度に応じたフォグ色と密度
- 距離と深度に応じた色吸収
- 画面空間の微粒子と気泡
- 潜水艦のライトコーン
- ソナー時の輪郭強調
- 被弾時の短い色収差とカメラ振動
- 爆発時の発光、衝撃波、気泡、残骸

初期版では高価なリアルタイム反射や体積流体を使わない。見た目の優先順位は、敵と魚雷の可読性、深度感、命中の迫力、環境の順とする。

### アセット読込

- ステージ共通アセットとステージ固有アセットを分ける。
- タイトルで全アセットを読まず、ミッション選択後に第1ステージ分をロードする。
- 重要モデルと効果音を先に読み、装飾アセットを後から準備できる構造にする。
- 読込失敗は対象URLと再試行操作を表示する。
- glTFとテクスチャは圧縮を検討し、解凍時間も計測する。

## 25. HUD

HUDはDOMで実装し、Canvas上へ重ねる。

| 領域 | 表示 |
| --- | --- |
| 中央 | 照準、ロック状態、対象名・距離 |
| 左下 | ソナー、Contact、アクティブパルス、緑色のロック対象 |
| 右下 | 武器、再装填、機雷、デコイ |
| 下中央 | 速度、深度、姿勢 |
| 左上 | HP、現在Objective |
| 画面端 | 敵、魚雷、被弾方向 |
| 下部 | AI相棒の字幕 |

HUD更新は毎描画ではなく、表示上必要な頻度に制限する。照準は描画フレームに追従し、数値類は10〜20Hz、Objectiveと装備状態はイベント時に更新する。

### レーダーのロック対象表示（実装済み）

- 現行HUDは約0.08秒間隔で更新する。接触情報は`id`、レーダー座標`x`／`y`、`boss`、`locked`を持つ。
- 表示対象は`alive && spawned && (detectedUntil > now || id === lockId)`。探知期限切れでもロック中の対象は残す。ロックを外した後は通常の探知期限に従う。
- 座標は実際に描画している自機の船首方向を水平面へ投影し、前方がレーダーの上になるよう計算する。
- 非ロックの通常敵は赤系の点、ボスは大きな橙系の枠付きマーカーで表示する。
- ロック対象には`target`クラスを付け、背景・枠・発光を緑色`#65ff8f`にする。`contactPulse`は0.7秒ごとに強弱を交互に変える緑色の発光とし、`z-index: 1`で他の敵マーカーより前に表示する。
- ボスにも緑色を適用し、通常敵より大きいマーカー寸法は維持する。
- 対象の切替に合わせ、中央の対象名・距離とレーダーの`locked`フラグを同じ`lockId`から更新する。

## 26. 会話システム

DialogueEntryは話者、字幕、音声URL、再生条件、優先度、割込可否を持つ。

- missionCritical：最優先。原則として省略しない。
- combatWarning：魚雷接近、低HPなど。短く、同種を連続再生しない。
- banter：AIの皮肉や雑談。戦闘警告が入ると中断または延期する。
- discovery：機体、記録、隠し経路の発見時に再生する。

字幕は音声の有無にかかわらず表示可能にする。音声を準備できない初期段階でも、同じデータ定義でテキストのみ動作させる。

## 27. オーディオ

### バス

- master
- music
- ambience
- effects
- voice
- ui

各バスの音量を設定から変更する。水中距離音はローパスと音量減衰を使い、重要な魚雷警告とAI音声は可聴性を優先する。

## 28. パフォーマンス目標

### 基準環境

発売時点で一般的なミドルレンジPC、1920×1080、最新の主要デスクトップブラウザを基準とする。実際の最低環境はプロファイリング後に確定する。

### 目標

| 指標 | 目標 |
| --- | --- |
| フレームレート | 60fps目標、最低30fpsを維持 |
| CPUフレーム時間 | 60fps時に16.7ms未満 |
| 初回操作可能時間 | 通常回線で5秒以内を目標 |
| ステージ読込 | 進捗表示し、30秒を超えない |
| ドローコール | 通常時300以下を目安 |
| 同時アクティブ敵 | 4〜6隻 |
| 同時魚雷・機雷 | 上限を設けてプール管理 |

### 対策

- EntityとProjectileのオブジェクトプール
- 遠方AIの低頻度更新
- InstancedMeshとLOD
- 影を重要ライトだけに限定
- ポストプロセスの品質プリセット
- テクスチャ解像度と圧縮の管理
- React購読範囲をselectorで限定
- renderer.infoとPerformance APIによる計測

low、medium、highの3プリセットを用意する。

| --- | --- | --- | --- |

## 31. エラー処理

| エラー | 挙動 |
| --- | --- |
| WebGL非対応 | 対応ブラウザとGPU設定の案内を表示 |
| アセット読込失敗 | 再試行、タイトルへ戻る、対象のログ |

## 38. 第2ステージ「灰燼の翼」（実装済み）

### ステージ定義と進行

`stages.ts`の`StageId = 1 | 2`と`STAGES`に任務名、海域、ボス名・HP、開始深度、記録点深度、会話を定義する。`GameShell`から`UnderwaterGame`へ`stageId`を渡し、ステージ切替時にはゲームを再マウントして敵、弾、タイマー、ロックを初期化する。

ブリーフィングに両ステージの選択ボタンを置き、ステージ1の結果画面からステージ2へ進める。`MissionResult.stageId`で結果と任務を対応付ける。保存バージョン3では`selectedStage`と`clearedStages`を永続化し、バージョン2以前のスコア・機体取得状況を保持したままステージ1選択・クリア履歴なしへ移行する。旧保存キーは維持する。

### 火山と噴煙

`VolcanicEnvironment.tsx`が海底、6基の円錐台状火山、発光する火口、観測ブイ、煙を描画する。ステージ2では氷床・氷塊・観測施設用の地形コライダーを使わない。

- 海底Y=-279。`VOLCANOES`の位置・底面半径・高さと上面半径7を、描画と`volcanicHeightAt`の両方で使用する。
- 自機の地形接触と魚雷の地形命中を同じ火山高さで判定する。開始点(0,-130,40)、記録点(0,-155,-395)には船体の空間を確保する。
- 火口ごとに100粒、計600粒のソフトなポイントスプライトを描画する。シェーダーで上昇と拡散を計算し、透明な煙は深度を書き込まない。
- `smokeDensityAt`で火口から上方175単位の煙領域を判定し、基本フォグ密度0.018に最大0.024を加算する。HUDは噴煙内を通知する。
- 火山本体に`SonarSurfaceMaterial`を使い、噴煙で視界が悪い状況でもソナーが進路の判断材料になる。

### ASH WING

指定画像2枚を参照し、Blender MCPでモデルを作成した。編集元・スクリプトは`assets/ash-wing/`、配信GLBは`public/models/ash-wing.glb`。船体と左右プロペラの3ノード、8描画以下、外部テクスチャなし。詳細は[モデル仕様](../assets/ash-wing/README.md)を参照。

`AshWingModel.tsx`は読込を共有し、左右のプロペラだけ個別に回転させる。船首-Z・上+Y、全幅約54。船体・翼も敵用ソナー反響に対応する。

ステージ2のボスはHP840、移動速度9、周回成分0.9。機体を速度方向へ向け、船首／船尾方向に2発、HP45%未満では3発の誘導魚雷を発射する。発射原点は機体中心から前後18単位とし、船体の外に置く。火山地形より上に高度を保つ。円盤型ボスの回転・外周発射はステージ1にのみ適用する。

### 撃破・クリアと検証

`combat.ts`の`damageEnemy`で魚雷・機雷のHP処理を共通化し、HPを0で止め、撃破を一度だけ通知する。機雷での最終撃でもボスクリアに進む。`completed`をクリア後も保持して敵魚雷のダメージを停止し、`completionReported`で結果通知の重複を防ぐ。

`tests/stage-two.test.mjs`では火山形状と衝突高さ、開始点・記録点の余裕、噴煙領域、魚雷・機雷によるボス撃破、GLBの翼幅・回転中心・発射余裕・描画量を検証する。既存のセーブテストにステージ選択・履歴の再読込、進行リセット、バージョン2からの移行を追加している。
